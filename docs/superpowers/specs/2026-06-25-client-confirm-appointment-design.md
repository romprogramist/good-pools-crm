# Подтверждение клиентом назначенного времени сервиса

**Дата:** 2026-06-25
**Проект:** good-pools-crm (Next.js 16 + Prisma 7 + Postgres)

## Проблема

Клиент сейчас сам выбирает желаемый диапазон дат (`desiredFrom`/`desiredTo`), а
сервисник при «Принять» сразу создаёт `Visit` — без участия клиента в финальном
согласовании. Нужно:

1. Урезать свободу клиента в выборе времени — он только сообщает «нужен сервис».
2. Сервисник принимает заявку и **назначает** время сам.
3. Клиент затем **подтверждает** или **отклоняет** назначенное время.

## Машина состояний

`OnlineRequestStatus` дополняется значением **`proposed`**.

```
pending  ──(сервисник назначает время)──▶ proposed
proposed ──(клиент подтверждает)─────────▶ accepted   (+ создаётся Visit)
proposed ──(клиент отклоняет)────────────▶ declined   (Visit НЕ создаётся, финал)
pending  ──(админ отклоняет, как сейчас)─▶ declined
```

Правила:

- Клиент при подаче указывает **только комментарий** — никаких дат.
- На шаге `proposed` `Visit` **не существует**; предложенное время хранится в полях
  заявки. Календарь сервисника при этом **не блокируется**.
- `Visit` создаётся **только** в момент подтверждения клиентом
  (`status = planned`, `kind = online_request`).
- Отклонение клиентом = финал. Заявка → `declined`. Чтобы записаться снова —
  клиент подаёт новую заявку с нуля.
- Так как слот не резервируется до подтверждения, два разных `proposed` могут
  указывать на одно время. На подтверждении делается **мягкая проверка
  занятости**: если слот уже занят — показываем предупреждение, но подтвердить
  всё равно можно (жёсткой блокировки нет).

## Изменения в данных (Prisma)

`OnlineRequestStatus` — добавить значение `proposed`.

`OnlineRequest` — новые поля для предложенного сервисником времени (заполняются на
шаге `proposed`, до создания `Visit`):

```prisma
model OnlineRequest {
  // ... существующее ...
  desiredFrom  DateTime?   // было required → nullable; из формы убираем
  desiredTo    DateTime?   // старые строки сохраняются; новые — null

  proposedServiceUserId   String?
  proposedAt              DateTime?
  proposedDurationMinutes Int?
  proposedNotes           String?
  proposedServiceUser     User?     @relation("OnlineRequestProposedBy", fields: [proposedServiceUserId], references: [id])

  declineReason String?   // уже есть — используем и для отказа клиента
}
```

- `desiredFrom`/`desiredTo` становятся **nullable** (не удаляем), чтобы не ломать
  историю существующих заявок. Из клиентской формы поля убираются.
- Различать «отклонил клиент» и «отклонил админ» отдельным полем **не нужно** —
  достаточно `declineReason`.
- Одна миграция Prisma (новый enum-value + новые столбцы + новая relation).

## Компоненты и потоки

### Клиент — подача заявки
- Файлы: `src/app/client/request-visit/page.tsx`, `createOnlineRequestAction`
  (`src/lib/server-actions/online-requests.ts`).
- Убрать поля дат. Остаётся: выбор бассейна + комментарий. Статус → `pending`.
- Проверка долга клиента — сохраняется как есть.

### Сервисник — назначение времени
- Файл: `src/app/service/online-requests/[id]/accept/page.tsx`.
- Та же форма (исполнитель + дата/время + длительность + заметки), кнопка
  переименовывается в **«Назначить время»**.
- `acceptOnlineRequestAction` → переименовать в `proposeTimeAction`: записывает
  `proposed*`-поля, статус → `proposed`, **`Visit` не создаёт**, шлёт push клиенту
  («вам назначено время … — подтвердите»).
- Гард: только `service`/`admin`, только при статусе `pending`.

### Клиент — подтверждение / отклонение
- Файл: `src/app/client/requests/page.tsx`.
- При статусе `proposed`: показать назначенное время и исполнителя + кнопки
  **«Подтвердить»** / **«Отклонить»** (отклонение — с полем причины).
- `confirmOnlineRequestAction`: мягкая проверка занятости слота → создать `Visit`
  (`planned`, `kind = online_request`), записать `visitId`, статус → `accepted`,
  push сервиснику/админу. Если слот занят — предупреждение, но подтверждение
  проходит.
- `rejectOnlineRequestAction`: статус → `declined`, записать `declineReason`,
  `Visit` не создавать, push сервиснику/админу.
- Гард: только владелец-клиент заявки, только при статусе `proposed`.

### Сервисник — список заявок
- Файл: `src/app/service/online-requests/page.tsx`.
- Добавить вкладку/бейдж **«Ожидают клиента»** для статуса `proposed`.

## Уведомления

Все push-уведомления — через существующий push-util (как в текущем
`acceptOnlineRequestAction`):

- `proposeTimeAction` → push клиенту.
- `confirmOnlineRequestAction` / `rejectOnlineRequestAction` → push
  сервиснику/админу.

## Вне зоны (YAGNI)

- Цикл «переназначить после отказа» — нет: отказ клиента всегда финальный.
- Таймаут/протухание подтверждения — нет.
- Отдельное поле «кто отклонил» — нет.
- Жёсткая блокировка слота / резерв до подтверждения — нет (только мягкая
  проверка).
- Выбор клиентом из готовых слотов / система доступности — нет.
